# Evolve — Android Wrapper

Packages [Evolve](https://github.com/pmotschmann/Evolve) (an incremental/idle browser game) as an
installable Android app — no browser tab held open to make progress — with a mobile-first redesign
of its UI layered on top (touch-sized controls, a bottom-sheet resource drawer, tap-vs-hold action
buttons, native save-to-file, and more; see [Mobile UI architecture](#mobile-ui-architecture) below).

See [`NOTICE.md`](NOTICE.md) for licensing (Evolve is MPL-2.0; this wrapper's own code is separate).

## Layout

```
game/          Evolve's source (HTML/CSS/JS) - originally a clone of pmotschmann/Evolve,
               now carrying a substantial mobile UI layer on top of it (see below).
               game/src/    hand-written source; game/evolve/ + game/wiki/ are its BUILT output.
android/       Native Android project, generated by Capacitor (`npx cap add android`)
capacitor.config.json   Capacitor config — webDir points at game/
package.json   Wrapper-level npm project (Capacitor CLI + core/filesystem/share deps)
```

`game/` is not passed through untouched. It's built from source (`game/src/*.js` → esbuild →
`game/evolve/main.js`; `game/src/*.less` → lessc/csso → `game/evolve/*.css`), and that source has a
real mobile UI pass on top of upstream — see the "Mobile UI architecture" and "Gotchas" sections
below before touching `game/src/`. The *built* output (`game/evolve/`, `game/wiki/`) is committed
alongside the source so the repo builds even if someone skips the `game/` build step by mistake, but
treat it as generated: always rebuild it after editing `game/src/`, never hand-edit it.

## How it works

Capacitor packages `game/` as local static assets inside a WebView-based Android app — no network
connection required at runtime, no browser chrome, and it gets a real launcher icon.

### Native capabilities added beyond stock Evolve

Two official Capacitor plugins are wired in for things a plain WebView can't do on its own:

- **`@capacitor/filesystem`** + **`@capacitor/share`** — Settings' "Save as File" writes the save to
  the app's own cache directory (no storage permission needed, unlike the shared Downloads folder)
  and hands it to Android's native share sheet, since the browser-only `<a download>` trick has no
  save-to-disk dialog to trigger inside a WebView.

Both are registered in **two** places, and both matter: the root `package.json` (so `npx cap sync`
picks them up and registers the native Android side) and `game/package.json` (so esbuild can resolve
the `import` when bundling `game/src/index.js`). Adding a Capacitor plugin means installing it in
both, not just one.

### "Runs in the background" — how this is actually handled

Evolve already has a **built-in offline/catch-up system** (`addATime` / `exceededATimeThreshold` in
`game/src/functions.js`): if more than 120 seconds pass between ticks, it detects the gap next time
it runs and fast-forwards progress (at a reduced 2/3 rate, capped). This is the same mechanism the
browser version uses when you leave the tab in the background or close it entirely.

That means the default, low-effort, battery-friendly setup is: **let Android suspend/kill the app
like it does any other app**, and rely on Evolve's own catch-up math when it's reopened — no
persistent notification, no foreground service, no battery-optimization exemption needed. This is
how most successful idle-game Android ports behave, and is the recommended starting point.

If literal live ticking while the screen is off is wanted later (not just catch-up-on-reopen), the
next step would be a foreground service hosting a headless WebView/JS engine with a wake lock and a
persistent notification — more battery cost and more Play Store scrutiny, so treat it as a v2
option, not the default.

## Mobile UI architecture

There is no separate "mobile build" — one JS bundle and one CSS file ship for every platform, and
mobile behavior is switched on at *runtime*, two different ways:

- **Layout/CSS** — nearly all of it lives inside a single `@media (max-width: 48rem)` block near the
  end of `game/src/evolve.less` (roughly a quarter of that file at this point). It activates purely
  on viewport width, so it also kicks in if someone just shrinks a desktop browser window narrow
  enough — it isn't gated on being inside the Android app.
- **Touch-specific JS behavior** (tap-vs-hold on action buttons, stepper glyphs, etc.) — gated by
  `isTouchInterface()` in `game/src/functions.js`, which checks for touch support + a mobile user
  agent + a user-facing "Touch Device" setting. `game/src/vars.js` flips that setting on
  automatically whenever `window.Capacitor` exists, so the packaged app gets it for free, but the
  check itself is generic and has nothing to do with Capacitor specifically.

Practically, this means: CSS changes are always safe to make broadly (they physically cannot affect
desktop layout outside the media query); JS changes to shared functions like `setAction()` or
`popover()` affect **both** desktop and mobile callers, so touch-only branches need their own
`isTouchInterface()` check rather than assuming the surrounding function is mobile-only.

## Gotchas

Non-obvious interactions this codebase's framework stack (Vue 2, Buefy/Bulma, LESS) produces, hit
and fixed repeatedly enough while building the mobile UI that they're worth knowing up front:

- **CSS specificity vs. `!important` vs. source order** — these are three *separate* tie-break
  tiers, checked in that order: `!important` always beats non-`!important`, full stop, regardless of
  specificity. Among rules that agree on `!important`-ness, higher specificity wins regardless of
  which one comes later in the file. Only among rules that are *equal* on both counts does later
  source order win. A mobile override that "should" win by sitting later in the file can silently
  lose to an earlier, more specific (or `!important`) desktop rule.
- **LESS nesting quietly raises specificity.** `.main { .content { .action { span.on {...} } } }`
  compiles to `.main .content .action span.on`, not just `.action span.on` — a flat mobile override
  of `.action span.on` can lose to it even though it looks like it targets the same thing.
- **Inline styles set via JS beat `!important` stylesheet rules — usually.** Vue's `v-show`
  directive, and jQuery's `.css('display', 'none')`, both set a *plain* (non-`!important`) inline
  style. Any `!important` stylesheet rule for that same property silently wins over it regardless of
  specificity, which breaks the intended hide/show. If you need a mobile style to lose to one of
  these JS-driven hides, drop `!important` from just that property and raise the selector's
  specificity to compensate instead. If a hide genuinely needs to always win (see
  `.action a.button span.count` in `evolve.less`), the fix is on the JS side: set the inline style
  with `element.style.setProperty('display', 'none', 'important')` instead of jQuery's `.css()`,
  which can't express `!important` at all — inline `!important` beats every stylesheet rule,
  `!important` or not.
- **Bulma's own base rules out-specificity flat custom classes more often than expected.**
  `.content ul`, `.content li + li`, `.columns.is-mobile` and similar carry a class *and* an element
  selector (or two), which beats a single custom class on specificity alone. Symptom: a margin/
  padding/wrap rule that looks correct in the stylesheet just doesn't apply. Check
  `getComputedStyle()` and the element's matched rules (not just your own rule) before assuming a
  typo — the fix is almost always `!important` or matching/exceeding the framework selector's
  specificity, not rewriting the rule.
- **`.columns.is-mobile` never wraps on its own.** Bulma's `.columns` only gets `flex-wrap: wrap`
  from the separate `.is-multiline` modifier; `is-mobile` just forces a flex row at every viewport
  width. A `.columns.is-mobile` row with more content than fits will overlap, not wrap, unless
  `flex-wrap: wrap` is added explicitly.
- **Touch tap-vs-hold can't rely on `mouseover` + `event.isTrusted`.** The obvious way to give a
  build/action button both "tap to run it" and "hold to see its description" is to open the
  description on `mouseover` and use `isTrusted` to tell a real hover apart from the touch-compat
  mouseover every browser synthesizes after a tap. That heuristic isn't reliable across every
  device/WebView. The fix in `functions.js`'s `popover()`: on a touch interface, don't bind to the
  real `mouseover` event at all — listen for a synthetic `evolve:popover-show` event instead
  (`MANUAL_POPOVER_TRIGGER`), which only a deliberate press-and-hold timer (see `setAction()` in
  `actions.js`, `bindHoldToShowInfo()` in `functions.js`) ever fires. The browser's own compatibility
  mouseover, trusted or not, then has nothing to trigger.
- **`<b-tabs>` is an inert placeholder until Vue actually mounts it.** Code that needs to touch the
  *real* rendered `nav`/`ul`/`li` structure (not just the `<b-tabs>` source tag) has to run after the
  relevant `new Vue({el, ...})` / `vBind()` call completes.
- **Passive touch listeners can't stop scroll-chaining.** A custom drag gesture (see the pull-up
  drawer in `index.js`) needs `{ passive: false }` and an explicit `preventDefault()` on `touchmove`
  to actually stop the browser's own scrolling while the drag is active — a passive listener can
  observe the touch but never suppress the browser's default handling of it. Direction-lock the
  gesture first (wait for a few pixels of movement, then decide vertical vs. horizontal) if the same
  touch zone also needs to allow an unrelated scroll in the other axis.
- **`--topbar-height` / `--bottomnav-height`** (CSS custom properties, synced by a `ResizeObserver`
  in `main.js`) exist because these bars' real rendered height varies enough (multi-line top bar,
  different themes/fonts) that a fixed guess in CSS drifted out of sync. Anything that needs to clear
  either bar should read these instead of hardcoding a height.
- **The established "label — number +" row pattern** is `.fuelItem` / `.factory` in `evolve.less`:
  a fixed-width label column on the left, then a flex-growing `.current` between `.sub`/`.add` that
  pushes the whole stepper flush to the row's right edge. New rows of this shape (a label plus a
  `.sub`/`.current`/`.add` triplet) should reuse this pattern rather than inventing another one — see
  its comment block in `evolve.less` for the full reasoning.

## Building

Prerequisites (all CLI-only — no Android Studio GUI required):

- **JDK 21** (Temurin) — this Capacitor version's Android libs target Java 21; JDK 17 fails the
  build with `invalid source release: 21`.
- **Android SDK**, command-line tools only: `platform-tools`, `platforms;android-36`,
  `build-tools;36.0.0` (Gradle also pulls `build-tools;35.0.0` transitively).
- `JAVA_HOME`, `ANDROID_HOME`, `ANDROID_SDK_ROOT` set and on `PATH` (a shell already open when you
  set these at the user/OS level won't see them until restarted).
- `android/local.properties` (gitignored, machine-specific) pointing Gradle at the SDK, e.g.
  `sdk.dir=C:/Android` — **forward slashes even on Windows**; a literal backslash path breaks the
  Java compiler step.

```bash
# 1. Wrapper-level deps (Capacitor CLI/core + the native plugins) — repo root
npm install

# 2. Game build deps (esbuild, lessc, csso) — separate package.json, separate install
cd game
npm install

# 3. Build the game itself: game/src/*.js -> game/evolve/main.js (esbuild),
#    game/src/*.less -> game/evolve/*.css (lessc + csso), and the same for game/wiki/.
#    Run this again after every change to anything under game/src/.
npm run build-win        # Windows; use `npm run build` on macOS/Linux
cd ..

# 4. Copy game/'s built output into the native Android project, and register
#    any Capacitor plugins (only needs re-running when native plugins change,
#    but harmless to run every time).
npx cap sync android

# 5. Build the APK
cd android
./gradlew assembleDebug   # -> android/app/build/outputs/apk/debug/app-debug.apk
```

To install it: enable Developer Options + USB debugging on your phone, plug in via USB, then either
`adb install app-debug.apk` or copy the APK over and open it directly (allow "install unknown apps"
for whichever app you use to transfer it).

### Iterating without a phone

For CSS/layout work, a real device isn't necessary every round:

1. Temporarily add `<script>window.Capacitor = {};</script>` to `game/index.html`, right before the
   `evolve/main.js` script tag — this forces `isTouchInterface()`/touch-only code paths on so a
   normal desktop browser behaves like the app does. **Never commit this** — it's a dev-only spoof.
2. Serve `game/` locally (`npm run serve` inside `game/`, or point any static file server at it) and
   open it in a browser at a narrow (≤48rem) viewport width, or with dev-tools device emulation on.
3. To test against real game state instead of a fresh save, drop an exported save file somewhere
   `game/` serves it from and import it via the console: `window.importGame(saveString, false)`.
4. Before committing: remove the `window.Capacitor` spoof from `index.html` and delete any temp save
   file — neither belongs in the repo.

Whenever you do move to a real APK build, don't skip steps 3-4 in "Building" above (`npm run
build-win` then `npx cap sync android`) just because the last one still built fine — Gradle packages
whatever's already sitting in `game/evolve/`/`game/wiki/`, it has no way to know those are stale.
